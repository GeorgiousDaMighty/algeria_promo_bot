# JET Algeria • Telegram tracker

Первая рабочая версия трекера промоутеров для запуска JET в Алжире. Интерфейс на французском, часовой пояс Africa/Algiers. Python 3.12+, стандартная библиотека, SQLite. Интеграции с API JET/SlickPay нет: кнопки фиксируют подтверждения промоутера, а не проверенные платёжные транзакции.

## Что реализовано

- Регистрация: имя и фамилия, привязка всех действий к неизменяемому Telegram ID.
- Один активный контакт на промоутера. `/start` восстанавливает текущий шаг, включая незаконченный инцидент. Закрытие Telegram не завершает контакт.
- Воронка: подошёл → интерес → телефон → JET установлен/аккаунт готов → SlickPay готов → попытка пополнения → успешное пополнение → поездка → дополнительный комментарий или пропуск.
- Номер телефона: начало `+213` или `213`, затем любые цифры, включая `0`. Ограничений на операторский префикс и длину нет. Ввод `213010121211` сохраняется как `+213010121211`.
- Инцидент на любом незавершённом этапе: кнопка, либо свободный текст на кнопочных шагах, либо вложение. На шагах ввода телефона/опроса текст является ответом; для инцидента там служит отдельная кнопка. После отправки возврат на тот же шаг. Описание обязательно; фото, видео, документы и голосовые сообщения необязательны. До 20 вложений на dossier. Альбом Telegram обрабатывается как несколько вложений: перед отправкой нужно дождаться подтверждения количества.
- Структурированное сообщение инцидента: ID, контакт, промоутер, время, этап, телефон (если уже известен), описание. Вложения отправляются ботом с номером инцидента, без пересылки исходных сообщений. Если телефон ещё не получен, это поле пустое.
- Ошибка оплаты создаёт инцидент на шаге проверки результата. После отчёта можно повторить проверку или прервать контакт с обязательной причиной.
- На первом шаге контакт можно прервать сразу, без причины и комментария. После перехода дальше прерывание требует причину и заключительный комментарий. Контакт сохраняется, история не удаляется.
- Отказы: нет времени, нет онлайн-средств, дорого, страх/не умеет, память телефона, нет смартфона/интернета, нет совместимого платежа, другое.
- Для проблем с оплатой: множественный выбор средств платежа, собственные варианты. Для «дорого»: приемлемая сумма в DZD. Для любого отказа: что изменило бы решение, либо «нет ответа», затем дополнительный комментарий.
- Ручное пополнение из меню: телефон, компенсация или промо, сумма DZD, комментарий. Работает и для новых, и для существующих клиентов, без обязательной привязки к текущей воронке. Это заявка, не начисление. Владелец отмечает выполненную заявку `/resolve ID` после ручной операции.
- Почасовые отчёты и суточный отчёт в 00:00 по Алжиру; после простоя пропущенные интервалы ставятся в очередь. Первый запуск начинает расписание с текущего часа.
- Отчёт за всё время и CSV выгрузка по кнопкам или `/report`, `/export` в личном чате. Доступ только владельцу и назначенным менеджерам.
- Назначение менеджеров, приглашения с проверкой вступления, отзыв доступа.

## Смысл аналитики

Часовой отчёт показывает события, произошедшие в интервале `[начало, конец)`, по каждому промоутеру. Отдельно показана конверсия **когорты контактов, начатых в этом интервале**, в поездку и количество незавершённых контактов. Конверсию нельзя считать делением поездок часа на подходы часа: это могут быть разные люди. Когортный блок отражает прогресс, известный на момент формирования отчёта; старые опубликованные сообщения не обновляются. `/report` пересчитывает актуальный результат за всё время.

Отчёт включает причины отказов и качественные ответы контактов этой когорты. CSV содержит журнал событий, автора, время, ID контакта, текущий статус и полные данные контакта в JSON. Один контакт встречается в нескольких строках, поэтому считать контакты надо по уникальному `contact_id`. Повторный подход к тому же человеку создаёт новый контакт: «контакты» не означают уникальных людей.

Данные хранятся в SQLite: `users`, `contacts`, `events`, `incidents`, `topups`, `managers`, плюс технические таблицы очереди и обработанных обновлений. Телефоны не включены в обычные агрегаты, но доступны менеджерам в инцидентах, заявках и экспорте. Вложения хранятся как Telegram file_id; независимого файлового архива нет.

## Запуск

1. Создайте Telegram-бота через BotFather, получите токен.
2. Создайте **закрытую супергруппу** менеджеров (в этой версии аналитика и инциденты идут в одну группу). Добавьте бота администратором с правами отправлять сообщения/медиа, приглашать и удалять участников. Владелец группы сохраняет контроль над её настройками.
3. Подготовьте числовой Telegram ID владельца и ID супергруппы вида `-100…`. После запуска любой пользователь может узнать свой ID командой `/id` в личном чате бота. ID группы можно получить из Bot API `getUpdates`, добавив бота и отправив группе команду **до запуска polling**. Не запускайте второго получателя обновлений одновременно.
4. Скопируйте `.env.example` в `.env` и заполните `BOT_TOKEN`, `OWNER_ID`, `MANAGER_CHAT_ID`. Токен храните в окружении сервера, не в GitHub. Репозиторий публичный.
5. На Linux-сервере с Docker Compose:

```sh
cp .env.example .env
# Заполните .env в редакторе
chmod 600 .env
docker compose up -d --build
docker compose logs --tail=100 bot
```

Контейнер использует постоянный volume `jet-data`. `docker compose down` его сохраняет; не используйте `down -v`, если данные нужны. Нужен исходящий HTTPS к `api.telegram.org`. Если бот раньше использовал webhook, отключите его в Telegram перед запуском: приложение намеренно не удаляет чужой webhook автоматически.

Для запуска без Docker на Linux/macOS:

```sh
export BOT_TOKEN='...'
export OWNER_ID='...'
export MANAGER_CHAT_ID='-100...'
export DB_PATH='./data/jet.sqlite3'
python bot.py
```

На Windows используйте Docker/Linux: блокировка единственного процесса использует `fcntl`.

## Доступ менеджеров

Команды выполняются владельцем в **личном чате бота**:

- `/grant 123456789` — предоставить пользователю доступ к отчёту и CSV.
- `/invite 123456789` — создать ссылку на закрытую группу с запросом вступления, действительную 24 часа. Бот возвращает ссылку владельцу, который передаёт её менеджеру. Запросы пользователей без роли менеджера отклоняются.
- `/revoke 123456789` — немедленно убрать доступ к аналитике бота и поставить удаление из группы в очередь Telegram. Проверьте права бота, если удаление не произошло. Уже скачанные выгрузки и прочитанные сообщения отозвать невозможно.
- `/resolve 42` — отметить ручную заявку №42 выполненной, уведомить группу и заявителя. Не вызывает JET API.

`/grant` сам по себе не добавляет человека в группу. Не создавайте параллельные публичные ссылки, если нужен контроль вступления через бота. Telegram-администратор группы по-прежнему может добавлять участников вручную.

## Надёжность и эксплуатация

Входящее обновление, изменение состояния, событие и исходящие сообщения фиксируются одной транзакцией. Повторные update_id игнорируются. Кнопки имеют версию состояния: устаревшая кнопка не начинает новый контакт и не подтверждает другой шаг. Один процесс на базу; горизонтальное масштабирование не предусмотрено.

Исходящие сообщения хранятся в outbox и повторяются с задержкой при ошибках. Telegram не поддерживает идемпотентный ключ для sendMessage: если API доставил сообщение, но ответ потерялся, возможен повтор с тем же номером dossier. Ошибки не удаляют запись инцидента/заявки. Постоянная ошибка прав или недоступное вложение может задержать последующие сообщения тому же получателю; нужно контролировать очередь и логи. Логи не содержат токенов, телефонов или описаний.

Для резервного копирования используйте SQLite backup API (он учитывает WAL), храните копии защищённо. Не копируйте только основной файл активной WAL-базы. Удаление данных по сроку хранения и внешний мониторинг в эту версию не включены; перед полевым запуском назначьте ответственного за бэкапы, права группы и обращения по данным.

Все активировавшие бота пользователи могут работать как промоутеры; отдельного списка допуска промоутеров пока нет. Менеджерские полномочия это не даёт. Переименование профиля из бота пока не поддерживается.

## Проверка

```sh
python -m unittest discover -s tests -v
python -m py_compile bot.py
```

Тесты без сети проверяют последовательность, восстановление состояния, дубликаты обновлений, устаревшие кнопки, инциденты, опрос, сумму, телефон, доступы, очередь и расписание. Перед работой в поле нужен один живой прогон с настоящим ботом: успешный контакт, отказ, инцидент с альбомом, заявка, приглашение и отзыв менеджера. Живой Telegram и Docker-сборка не проверялись без окружения развёртывания.

## Настройка

Тексты, варианты причин и платежей находятся в `bot.py` (`STAGES`, `REASONS`, `PAYMENTS`, `prompt`). Список платежей нужен для исследования привычек пользователей, **он не означает**, что JET/SlickPay поддерживает каждое средство. Переход «SlickPay готов» предполагает требуемую бизнесом настройку, но не проверяет её технически. Бот не публикует непроверенных ссылок на приложения: промоутерам нужно выдать официальные локальные ссылки отдельно.
